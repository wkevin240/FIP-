# Journal reversal tenant boundary\n\nA journal reversal is a new `journal_entries` row that points to its original entry through `reversal_of_id`. The database must not allow that reference to cross organization boundaries.\n\nMigration `20260913_0021` adds a composite uniqueness constraint on `(organization_id, id)` and a composite foreign key from `(organization_id, reversal_of_id)` to the same columns on `journal_entries`. PostgreSQL therefore rejects a reversal whose organization differs from the organization of the original journal entry.\n\nThe existing application service already scopes reversal lookup by organization. This migration makes the invariant durable for direct SQL, background jobs, migrations, and any future write path that bypasses the service.\n\nThe existing unique constraint on `reversal_of_id` continues to enforce one reversal per original entry. A same-organization reversal remains valid.\n\n## Verification boundary\n\n`test_journal_reversal_tenant_postgres_integrity.py` exercises the deployed PostgreSQL constraint with real DML. It proves both rejection of a cross-organization reversal and acceptance of a same-organization reversal. The fixture transaction is rolled back and creates no persistent business data.\n\nNo OHADA classification, tax rule, seed, or regulatory interpretation is introduced.\n
